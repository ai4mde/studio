OOUI Design04 / 12

UML-to-Interface Mapping Logic

Create pages first, then attach sections, components, and fields.

Mapping Logic

Page-section construction: UML elements move into a small interface DSL — every page owns sections, every section owns a component, fields, and operations.

  1. Create pages from goals: use cases and activity workflows decide which pages exist.
  2. Attach sections to pages: the primary class becomes the section data source.
  3. Choose section components: collections use cards/grids; input tasks use forms.
  4. Bind fields and actions: class attributes become fields; use case actions become operations.

LLM Candidate Generation & HITL

The LLM designs layout and style; human feedback drives refinement.

  1. Generation contract: model receives page/section skeletons — it edits DSL metadata, not arbitrary code.
  2. Force diversity: three candidates must vary on layout, density, page width, and theme.
  3. HITL loop: designer picks a candidate and gives feedback — regeneration refines the pick, not restarts.
Generate 3 candidates · vary: layout / density / width / theme
Regenerate (HITL): BASE = selected candidate · vary unlocked axes only
Preserve: UML bindings · page identity · section roles

LLM Generation & HITL06 / 12

Validation & Interface DSL

LLM output is validated against a structured Interface Meta Data DSL.

Reliability Layer

LLM output is only a proposal: every candidate is checked before it reaches the renderer. One DSL connects all layers — UML extraction, LLM design choices, validation, and Django rendering.

  1. DSL schema contract: only supported layout identifiers, operations, styling fields, and tokens can be edited.
  2. UML-bound attributes: generated fields are checked against classifier attributes to prevent hallucination.
  3. Styling tokens: visual changes use predefined token keys, not arbitrary CSS.
  4. Fallback handling: invalid sections are normalized to keep rendering stable.

Case Studies

Four systems test the pipeline across domains, roles, and workflow complexity.

Evaluation Coverage

Multiple domains, shared pipeline: each case study starts from UML-derived metadata and is rendered through the same page-section-component DSL.

  1. Domain variety: healthcare, library management, ecommerce, and loan processing.
  2. Role complexity: customers, staff, administrators, and applicants across systems.
  3. Workflow complexity: activity flows test whether generated pages support multi-step tasks.
  4. Object-centric structure: classes, attributes, and relations test whether pages remain grounded in UML models.

Case Studies08 / 12

Evaluation Results

Results are strongest for usability and utility; weaker for refinement precision.

Study Design

Lightweight user study: 9 participants explored all four case studies with Likert-scale and open-ended questions; 5 completed a detailed questionnaire on roles, workflows, OOUI navigation, diversity, and HITL.

  1. Utility is high: time saving 4.4 · willingness to use 4.1.
  2. Usability is strong: feedback clarity 4.8 · overall usability 4.2.
  3. Model structure is visible: role separation and object-centric navigation both 4.0.
  4. Refinement is the weak point: candidate diversity 3.6 · HITL refinement 3.5.

Evaluation Results09 / 12

Limitations & Future Work

The approach works, but the evidence and refinement loop are still early-stage.

The evaluation is promising, but not yet broad enough for strong generalisation.

Remaining Issues

Early-stage evidence: the prototype demonstrates feasibility, but the study and refinement loop need strengthening.

  1. Small evaluation sample: 9 participants completed the study, 5 the detailed questionnaire.
  2. Refinement precision: HITL regeneration works, but feedback is not always reflected accurately.
  3. Future work: improve onboarding, data binding reliability, prompts, visual hierarchy, and run a larger evaluation.
Limitations & Future Work10 / 12

Conclusion

LLMs can enhance MDE UI generation when constrained by UML, DSL schemas, validation, and human feedback.

Final Findings

MDE and LLMs can work together: the model-driven layer preserves structural correctness, while the LLM layer improves diversity, adaptability, and designer-directed refinement.

  1. H1 supported: generated interfaces remain organized around UML-derived objects, attributes, and relationships.
  2. H2 supported: use case and activity metadata enable actor-specific and workflow-aware enterprise interfaces.
  3. H3 partially supported: HITL regeneration works, but refinement precision still needs improvement.
